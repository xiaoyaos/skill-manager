# 周报规范

本文件定义 `git-weekly-report` 的数据契约、写作口径和 Excel 版式。脚本和模型都以此为准。

## 1. 数据流

```text
git log
  -> commits.json     # 证据：谁、哪天、哪个仓库、哪条提交
  -> report.json      # 叙事：重点项目 / 日常工作、目标、进展、状态、偏差
  -> 周报.xlsx        # 交付：固定版式、A4 横向、单页
```

- `commits.json` 由 `scripts/extract_commits.py` 生成，不手改。
- `report.json` 由模型根据 `commits.json` 编写，是唯一需要人工/模型判断的中间产物。
- `周报.xlsx` 由 `scripts/render_report.py` 生成，不手改；改内容请改 `report.json` 后重新渲染。
- `scripts/validate_report.py` 负责覆盖、字段、证据和版式校验。

## 2. 周期

- 默认周期：上一个 ISO 周，周一至周日。
- `period` 格式：`YYYY/MM/DD-YYYY/MM/DD`，例如 `2026/10/19-2026/10/25`。
- `week` 格式：`W43`；同时保留 `iso_year`，避免跨年周歧义。
- 单周模板要求起止日期落在同一个 ISO 周。跨周范围先和用户确认，不要直接套单周模板。

## 3. `report.json` 结构

```json
{
  "period": "2026/10/19-2026/10/25",
  "week": "W43",
  "sections": [
    {
      "label": "重点项目",
      "items": [
        {
          "name": "示例平台接入与鉴权",
          "goal": "完成平台应用接入、租户白名单与网关鉴权能力。",
          "progress": "实现应用类别透传与租户列表返回；修复应用无角色时的处理；调整请求限制并补充鉴权主体字段说明。",
          "status": "完成",
          "deviation": "无",
          "evidence": {
            "projects": ["Example Platform"],
            "repos": ["platform", "packages/platform-gateway"],
            "commit_count": 6,
            "sample_commits": [
              "内部微服务豁免租户白名单并返回应用类别",
              "鉴权主体新增应用类别与租户列表",
              "修复应用无角色时处理"
            ]
          }
        }
      ]
    },
    {
      "label": "日常工作",
      "items": []
    }
  ]
}
```

### 字段契约

| 字段 | 必填 | 规则 |
|---|---|---|
| `period` | 是 | 必须与 `commits.json` 的 `period.label` 一致。 |
| `week` | 建议 | 必须与 `commits.json` 的 `period.week` 一致。 |
| `sections` | 是 | 至少一个 section；当前固定使用“重点项目”和“日常工作”。 |
| `label` | 是 | section 名称，会竖排显示在 A 列。 |
| `items` | 是 | 每个 section 至少一条；没有内容时不要创建空 section。 |
| `name` | 是 | 8-30 字，写关键结果，不写仓库名，不写 commit 标题堆砌。 |
| `goal` | 是 | 一句话说明目标；重点项目优先使用项目映射里的标准 `goal`。 |
| `progress` | 是 | 2-5 个分句，用中文分号 `；` 分隔；动词开头；写具体技术名词。 |
| `status` | 是 | `完成` / `进行中` / `部分完成` / `有偏差`。 |
| `deviation` | 是 | 状态为 `完成` 时写 `无`；否则写具体原因，不能写 `无`。 |
| `evidence.projects` | 是 | 对应项目名，必须出现在 `commits.json.stats.by_project` 中。 |
| `evidence.repos` | 建议 | 支撑条目的仓库路径，便于审计。 |
| `evidence.commit_count` | 是 | 支撑条目的提交数，必须大于 0，且不超过对应项目实际提交数。 |
| `evidence.sample_commits` | 是 | 1-5 条真实提交标题；单提交条目可为 1 条，其余建议 2-5 条。 |

## 4. 选材规则

### 重点项目（建议 3-5 条）

满足任一条件：

- 战略性、功能级、跨多天或跨多仓库。
- 对用户可见，或涉及架构、协议、核心链路、数据迁移。
- 单个项目提交很多时，按主题拆成 2-3 条，而不是逐条罗列提交。

### 日常工作（建议 2-4 条）

- 小修复、文档、配置、构建、环境维护。
- 单条或少量提交，但确实占用了工作时间。
- 不要为了凑数把重点项目拆成日常。

### 总量

建议不超过 8 条。超过 8 条时优先合并同类项，保证 A4 横向单页可读。

## 5. 完成状态口径

| 状态 | 使用条件 |
|---|---|
| `完成` | 本周工作闭环，无遗留。 |
| `进行中` | 已启动、按计划推进，但本周未闭环。 |
| `部分完成` | 多个子项只完成一部分。 |
| `有偏差` | 有阻塞、延期或范围变化。 |

状态不是 `完成` 时，`deviation` 必须写原因，例如“等待第三方接口联调”“硬件环境未到位”“范围新增，顺延到下周”。

## 6. 写作规则

- 用中文书面语，不用第一人称。
- 不写 commit hash、分支名、内部工单号。
- 不写“相关工作”“其他优化”这类无法审计的表述。
- 不编造上线、发布、客户验收、性能指标；除非提交或用户明确提供。
- 优先写：表、接口、字段、页面、协议、模板、迁移、配置、链路。
- `progress` 用分号分隔，每个分句一个动作，避免长句套长句。
- 同一件事不要同时出现在重点项目和日常工作。

## 7. Excel 版式

### 页面

- A4 横向。
- 页边距：左 0.3、右 0.3、上 0.4、下 0.4 英寸。
- `fitToWidth=1`、`fitToHeight=0`、`fitToPage=True`。
- 不显示网格线。
- 打印标题行：`1:2`。

### 行结构

| 行 | 内容 |
|---|---|
| 1 | 标题：`周报周期：<period>`，合并 A1:F1，浅蓝底。 |
| 2 | 表头：`大类`、`名称（只列关键）`、`目标`、`进展`、`完成状态`、`偏差说明`。 |
| 3 起 | 第一个 section 的数据行。 |
| section 之间 | 一行高度 8 的分隔行。 |
| 最后 | 第二个 section 的数据行。 |

### 列宽

| 列 | 宽度 |
|---|---|
| A | 8 |
| B | 24 |
| C | 34 |
| D | 68 |
| E | 10 |
| F | 22 |

### 样式

- 字体：宋体。
- 标题：14 号、加粗、颜色 `1F4E79`、底色 `D9E2F3`、行高 30。
- 表头：11 号、加粗、白字、底色 `1F4E79`、行高 30。
- 大类列：11 号、加粗、颜色 `1F4E79`、底色 `E2EFDA`、竖排、按 section 合并。
- 数据行：11 号；名称加粗；完成状态居中；其余左对齐、顶端对齐、自动换行。
- 边框：细线 `BFBFBF`。

### 行高估算

```text
text_units = 中文字符按 2，其他字符按 1
lines = max(
  1,
  ceil(text_units(name) / 20),
  ceil(text_units(goal) / 32),
  ceil(text_units(progress) / 64),
  ceil(text_units(deviation) / 22)
)
height = clamp(lines * 15 + 10, 30, 409)
```

行高是估算值，渲染后仍需打印预览确认。文字被截断时优先缩短 `progress`，不要直接缩小字体。

### 单页检查

`validate_report.py` 会按列宽估算横向缩放比例，再估算缩放后的总高度：

- 可用纸张：A4 横向 11.69 × 8.27 英寸。
- 可用宽度 = 11.69 - 左右页边距。
- 可用高度 = 8.27 - 上下页边距。
- 若估算总高度超过可用高度，校验失败，提示压缩内容或调整行高。

## 8. 校验规则

### 错误（必须修复）

- `period` 与 `commits.json` 不一致。
- `unmapped` 非空。
- 有提交的项目没有被任何条目的 `evidence.projects` 覆盖。
- 必填字段为空。
- `status` 不在允许值内。
- 非 `完成` 状态但 `deviation` 为 `无`。
- `evidence.commit_count <= 0`，或超过对应项目实际提交数。
- Excel 标题、表头、section 合并、打印设置不符合版式。
- 估算内容超过 A4 横向单页。

### 警告（建议修复）

- 重点项目不在 3-5 条。
- 日常工作不在 2-4 条。
- 总条目超过 8 条。
- `sample_commits` 在提交记录中找不到对应标题。
- Excel 中存在报告之外的额外行。

## 9. 隐私与仓库边界

- 真实 `config.json`、`project-map.json` 放在 `~/.config/git-weekly-report/`，不提交。
- 仓库只保留 `*.example.json` 作为配置示例，不包含真实项目名和邮箱。
- `commits.json`、`report.json`、生成的 `.xlsx` 都是本地产物，不提交。
- 示例中的邮箱、项目名、提交标题必须脱敏。

## 10. 后续扩展

- 多周详细周报：按周分块，复用 `commits.json`，新增 renderer。
- 手工补充项：会议、方案、客户支持等无 commit 的工作，通过独立输入文件合并。
- 团队统计：支持多作者和按人分组，但需要新的权限与隐私约定。
