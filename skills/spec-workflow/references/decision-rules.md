# 循环控制与升级规则

验收后由主会话按本规则判定：能收敛就自动收敛，不能收敛就尽早交给用户，杜绝空转。

## 每轮记录

每轮验收后，在 rounds.md 追加：

- 轮次；
- 未通过 AC 编号；
- blocker/major/minor 数；
- 是否发生回归；
- 结论（通过/回实现/升级）。

同时保留 acceptance.md 中的命令结果与文件行证据。不得只记录数量而丢失问题身份。

## 进展判定

- **回归**：上一轮已通过的 AC 本轮失败，或出现新的 blocker。
- **有进展**：无新增 blocker、无回归，且未通过 AC 数比上一轮严格下降。
- **无进展**：未通过 AC 数持平或上升，或虽数量下降但新增 blocker/发生回归。
- 第一次验收没有上一轮数据，只建立基线；没有 blocker 时允许进入一次修复轮，其后必须严格遵守进展判定。
- “同一问题连续两轮”按同一 AC 的同一根因判断，而不是只看文案是否相同。

## 循环决策（按顺序）

1. 全部 AC 通过 → `awaiting-merge-approval`。
2. 存在 blocker 且本轮未解决 → `escalated`。
3. 发生回归 → `escalated`。
4. 同一 AC 的同一根因连续两轮出现 → `escalated`。
5. 本轮无进展 → `escalated`。
6. 已完成 3 个实现-验收轮次仍未通过 → `escalated`。
7. 否则 → `implementing`，带完整问题清单进入下一轮。

修复轮必须批量处理本轮所有 blocker/major/需要代码修改的 minor，不得一个问题派发一次。

## 问题分级与处理

| 级别 | 判定 | 处理 |
| --- | --- | --- |
| blocker | 阻塞核心功能、安全、数据正确性或无法验收 | 必回实现；一轮未解决即升级 |
| major | 结构性、跨模块或影响主要行为 | 回实现，附完整证据 |
| minor | 文案、格式、命名或单点问题 | 非行为性修改由主会话当前轮复核；涉及代码、测试或行为则回实现 |

主会话直接修复 minor 时必须满足：

1. 不改接口、代码逻辑、测试含义或运行行为；
2. 记录修改内容；
3. 让 reviewer 对受影响的 diff 和 AC 做只读复核；
4. 不新增轮次。

任一条件无法满足，交回 implementer 并开启新轮。

## 计划变更

实现或验收过程中发现 AC 不可达、范围错误或方案需要改变时：

1. 立即停止修复循环；
2. 回到 `planning`；
3. 修订 plan.md，保留既有 rounds.md 证据；
4. 重新请求计划确认，确认前不得继续实现。

## 升级 = 停下问用户

升级时：

1. 将 status 置为 `escalated`；
2. 报告卡点、已完成轮次、每轮未通过 AC 与严重度变化、回归和已尝试方向；
3. 给出“继续修复 / 回到计划 / 放弃”的建议；
4. 未经用户明确指示不得继续循环。

## 效率原则

- 自检不额外派子代理：计划和验收出口由主会话自检，实现出口由 implementer 自检、主会话复核。
- 修复轮只重跑受影响 AC 的验证，但 reviewer 必须确认未触及的已通过 AC 未回归。
- 达到阈值只代表可以请求用户确认，不代表已获得合并、发布或外部副作用权限。
